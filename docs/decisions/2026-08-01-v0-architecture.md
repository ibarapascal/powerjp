# 2026-08-01 — v0 架构决定

> 本文记录 powerjp 立项时的架构决定与被否决的选项。
> 目的：防止将来重新讨论已经定过的事。被否决的选项和理由一起记，否则半年后会原地绕回来。
> 结构：每节 = 一个决定 + 选它的理由 + 否决了什么。
> 更新规则：本文件**不改**。决定变了就新写一份 ADR 并在此标注「已被 YYYY-MM-DD-xxx 取代」。

## 背景

起点是一份日本电网公开数据源的盘点：发电侧近乎全透明；网侧的拓扑与空容量法定公开但**官方矢量坐标不存在**，唯一带坐标的源是 OSM 众包整理；需求侧区域级全透明，再往下逐级变暗。目标是把这些拼成一个可视化 + 分析站点。

## 1. 范围：v0 = 地图底座 + 准实时层

**选**：网络几何 + 发电点 + 区域逐时需给 + 基干潮流 + 价格。

**否决**：
- *只做静态地图底座* —— 没有时间维度就只是一张图，价值太低。
- *加市町村级需求层* —— 引入 CC-BY-NC 许可污染；且该数据集的逐时形状按 TSO 统一分配，同一区域内所有市町村曲线形状完全相同，容易被误当真值使用。

**连带决定**：需求侧分辨率止于 10 区域。建筑颗粒度明确不做，配电级几何不做。

## 2. 分发：纯静态预计算推 CDN

**选**：后端只跑管线，产出瓦片与 Parquet 分片推 Cloudflare R2，前端直读 CDN。

**理由**：站点无鉴权无登录态，纯静态天然满足；**パイプライン側が落ちてもサイトは生きる**；成本近零；**后端不需要对公网暴露任何端口**。

**否决**：
- *暴露公开只读 API* —— 无鉴权で公開すると濫用のリスクがあり、**パイプライン側の停止がそのままサイト停止になる**。
- *混合（几何静态 + 时序走 API）* —— 两套分发路径，复杂度翻倍，换不来相称的收益。

**代价**：任意时间范围的聚合查询需要前端下载分片自行计算。接受。

## 3. 编排：Dagster

**选**：Dagster，以 `dagster dev` 运行。

**理由**：software-defined assets 直接对应「每个数据层是一个资产、声明上下游、上游更新自动触发下游重算与发布」的需求；自带 UI 可看血缘与物化历史，是主要的状态观察入口。

**否决**：
- *Prefect* —— 任务导向而非资产导向，「上游变了自动重算下游」要自己实现。
- *自写 Python + Makefile + cron* —— 依赖图和增量重算全靠手写，源一多就失控，且没有现成 UI。

## 4. 存储：PostGIS + Parquet 分工

**选**：几何与拓扑进 PostGIS，时序落 Parquet 文件。**Parquet on disk 是 SSOT**，Dagster 只记 metadata 不管理文件。

**否决**：
- *纯 DuckDB + Parquet* —— 可复现性最好，但空间拓扑操作（连接关系修复、N-1）弱于 PostGIS。
- *全进 PostGIS* —— 心智负担最小，但导出给 CDN 多一道，且他人复现要起数据库。

## 5. Ingest / Process 分界线 = `storage/raw/`

**选**：把「把文件搞进 raw/」和「从 raw/ 开始处理」彻底分开。前者方式不统一、可人工、可要凭据、不进自动化；后者完全确定性。

**理由**：需要注册或登录的源（GEM、OCCTO）不再是管线里的异类，它们只是不同的 ingest 类型。管线本身永远从 raw/ 出发，永远可重放。

**来源**：別の同種プロジェクトで実績のある構成を踏襲したもので、独自の発案ではない。

## 6. 瓦片格式：`{z}/{x}/{y}.pbf` 目录，不用 PMTiles

**选**：tippecanoe 输出目录结构，直接放 R2。

**理由**：前端定了 Mapbox GL JS，而 PMTiles 依赖的 `addProtocol` 是 MapLibre 的 API。

**否决**：*PMTiles 单文件* —— 与 Mapbox GL JS 不兼容。*Mapbox Studio 托管 tileset* —— 数据托管到第三方，有配额，对开源不友好。

## 7. 正确性保障：人工 e2e + metadata 数字

**选**：不建测试目录，不引数据契约库，不做断言阻断。每个 asset 在 metadata 里记行数、大小、路径、时间范围；可视化 asset 额外记 `demo_url`，Dagster UI 里点开直接看地图。

**理由**：项目的主要失效模式是「数据看起来对但其实不对」，这靠单元测试抓不到，靠看地图能抓到。metadata 数字补上肉眼看不出的那类（数量级突变）。

**否决**：*完整测试套件* —— 与「优先速度和实用性」的取向不符，且对这类以数据为主的项目性价比低。

## 8. 前端：M1 起就用 web/，不做一次性 debug 页

**选**：React + Vite + Mapbox GL JS，第一天就建，初期极简（底图 + 图层开关 + 时间轴），每进来一层数据加一个开关。

**理由**：验证工具和最终产品是同一个东西，逐步长大，不写抛弃型代码。布局、交互、叙事等「编排」工作后置。

**否决**：*独立的 MapLibre debug 单页* —— 与最终前端技术栈不同，等于写两遍。

## 9. 公开策略：另起 repo，不改写历史

**选**：private repo 保留完整开发历史；公开时新建 public repo，用当时的工作树做 initial commit。

**理由**：删文件不会从 git 历史移除内容；改写历史后 GitHub 上已 push 的 blob 仍可能通过原 commit SHA 访问。另起 repo 是零风险路线。

**代价**：public repo 没有开发历史。接受。

**2026-11 更新（取代上文的选择）**：改为在原 repo 用 `filter-repo` 清理历史后公开，保留开发历史；旧 SHA 残留的处理见 `LESSONS.md` #4。

**连带纪律**：凭据永不进 git（任何 repo，private 也不行）；机器身份与非公开判断放另一个 private repo，通过 `CLAUDE.local.md` 的一行 import 引入。

## 10. 推进顺序

```
1. 点线网络  →  2. 潮流  →  3. 需求  →  4. 各类电
   （以上纯搬运，每进一层立刻可视化验证）
5. 计算中间层：供需空洞、各类需求，之后按需加
```

**「供需空洞」的定义**（钉死，防跑偏）：逐时 × 带网络约束的到达性洼地 —— 某区域某时刻本地供给够不够、是否依赖外部输入、通道容量够不够、何时最紧。**不是**「再生能源发电量 ÷ 当地需求」的年度能量账。
