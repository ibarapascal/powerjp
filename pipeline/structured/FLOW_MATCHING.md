# 潮流 → 真实几何

> 目的：把 `occto_flow` 的**逐线潮流**接到真实走线几何上，让线在地图上动起来。
> 结构：现状 → 为什么放弃名字匹配 → 图路径求解 → 三道守卫 → 缺口 → 走不通的路。
> 更新规则：覆盖率变化、新增守卫、或**口径变更**时更新。
> 工具：`flow_match_probe.py`（名字匹配）/ `flow_route_probe.py`（**图路径，主力**）。

## ★ 電圧制約を外してはいけない（2026-08-02）

経路探索は 2 段構えになっている：

```python
# ① 厳格：その電圧の辺だけを通す
allowed = {275.0}
if allowed_kv and kv and kv not in allowed_kv: continue
#                 ↑ 辺の kv=0（OSM 未記載）は通す。「不明」であって「低圧と判明」ではない

# ② 厳格で解けないときの再試行
c = route(adj, s, g, None)     # ❌ かつてはここで**制約を全部外していた**
```

②が原因で、**275kV の幹線が 66/77kV の配電線を延々と辿る経路**が生まれていた：

```
中部 高根中信線 (275kV)   62 区間が 66/77kV 上
中部 川越火力線 (275kV)   43 区間
東京 千葉葛南線 (275kV)   22 区間
```

該当したのは **12 本**（335 本中）で、`kv_mismatch` 区間 178 はすべてここ由来。
厳格段階からは 1 区間も出ていない。

**対策**：②を「**隣接する電圧階級まで**」に限定（`KV_NEIGHBOURS`。275↔220 のみ、
他は自分自身）。この定数は元からあったのに、回退分岐だけ `None` を渡していた。

| | 変更前 | 変更後 |
|---|---:|---:|
| 真実幾何 | 72.2%（335 本） | **68.3%（317 本）** |
| `kv_mismatch` 区間 | 178 | **0** |
| 電圧制約下で経路なし | — | 40 本 |

40 本は「電圧を守る限り通り道が無い」線路。以前はそれを無理に繋いでいた。

## ★ 区間の品質と描画の可否

⛔ **誤った幾何は出力しない**（ユーザー方針「不能画错的」）。

| 品質 | 判定 | 描画 | 実測 |
|---|---|:-:|---:|
| `real` | 実幾何あり・電圧整合 | ✅ | 645 |
| `short_gap` | 幾何なし（直線代用）だが **< 1.5km** | ✅ | 39 |
| `straight` | 幾何なしで長い → **実在しない直線** | ❌ | 2 |
| `kv_mismatch` | 段電圧 < 線路公称の 50% | ❌ | 0（対策後） |

⚠️ **段電圧 0（OSM 未分類）は誤りとみなさない。**

「幾何なし」は `load_graph` が幾何を持たない辺を両端の直線で代用しているため
（AJG 19,031 辺中、幾何ありは 14,048）。近接した接続欠落は残し、長いものは捨てる。

### 電圧が 3 つ出てくるので整理

| 呼び方 | フィールド | 出所 | 粒度 |
|---|---|---|---|
| **線路公称電圧** | `line_kv` | OCCTO 潮流 CSV の「電圧」欄 | 線路に 1 つ |
| **段電圧** | `kv` | AJG グラフ上、経路が通る各辺 | 区間ごと |

「公称電圧」は線路公称電圧の別名（同じもの）。

- **線幅**は段電圧で決める → 下の送電線と区間ごとに揃う
- **負荷率**は線路公称電圧で決める → 潮流値は線路全体の値なので、
  低電圧の区間で割ると 77kV 区間が 706MW のような破綻をする

## ★ 幾何の重なりは放置する

異なる線路が同じ区間に載ることがある（**156 区間 / 23%**）。
経路探索は両端しか知らないので別々の線路が同じ辺を通る一方、
日本は**同塔並架**が多く、重なりが物理的に正しい場合もある。
**データからは両者を区別できない。**

⛔ オフセットで描き分けない（2026-08-02「因为线宽也有定义，所以就重叠得了」）。
線幅は電圧で一意に決まる決まりであり、オフセット量を線幅に追従させると
幅の定義が二重になる。`shared_count` / `shared_with` で本数だけ示す。

## 剩下那一半基幹线为什么没有潮流数据

查过 OCCTO 的 464 条线名，**大部分不是「没公表」，是我们没对上**：

| AJG 里「无潮流」的线 | 实际在 OCCTO 里 |
|---|---|
| 福島幹線 (236.8 km) | ✅ **`福島幹線(中)`、`福島幹線(里)`** —— 括注是回线区分 |
| 越美幹線 (220.0 km) | ✅ `越美幹線` |
| 三岐幹線・伊勢幹線・朝日幹線・南近江線・安曇幹線 | ✅ 全都有 |

分三类：

**A. 名字形态差异（我们的问题）**：`福島幹線` vs `福島幹線(中)/(里)`；
分段命名 `常磐幹線` vs `常磐南幹線`/`常磐北幹線`。

**B. 路径求解失败（我们的问题）**：名字对得上但几何没连上，见下面的缺口分析。

**C. 真的不在这份数据里**：
- **地域間連系線** —— `関門連系線` 没有，且 **464 条里「連系」出现 0 次**。
  OCCTO 把**連系線**和**地内基幹送電線**分成两套公表，我们只取了后者。
  **这是明确的、可补的新数据源**（见 TODO）。
- **電源線** —— `下郷線`/`奥只見線`/`沼原線` 全是揚水·水力电站的引出线，
  不属于「地内基幹送電線」的公表对象。

**可解的已经 100% 解出** —— 两端都能定位的是 323 条，全部求出了路径。
剩下的 30.4% 全部卡在**端点在图里找不到**，不是路径算法的问题。

对比：纯名字匹配（`flow_match_probe`）的真实几何只有 **47.0%**（路 A）
或 62.5%（路 A ∪ 端点对反查）。

## 为什么放弃名字匹配

OCCTO 的干线名在 OSM 里**根本不存在**：

```
篠路線・北本七飯線・常磐南幹線・常磐北幹線・０１２９線・
宮城幹線・五頭幹線・吾妻幹線・山形幹線・新潟幹線・相福幹線・中越幹線 …
```

试过的补救（都做了，收益极小）：

| 改动 | 路 A 提升 |
|---|---:|
| 按 `/` 拆多回线（`那珂線 / 阿武隈線`） | |
| 剥 `【増強後廃線】`『（山線）』括注、`1L/2L` 回线标记 | |
| `幹線` ↔ `線` 互为变体 | |
| 合计 | 47.0% → **48.5%** |

索引名从 11,409 涨到 17,833，覆盖只 +1.5pt。**名字这条路到头了。**

## 主力方案：在图上求路径

不匹配名字，直接求**物理路径**：

```
AJG docs/data/built/all.json
   nodes 17,333  {id, lat, lon, kv, main, deg, sub, name, region}
   edges 19,031  {a, b, kv, par, name, path}   ← path 是完整几何
```

1. 用潮流的两端站名在图里定位起终点节点
2. **Dijkstra**，边权 = 实际线路长度（haversine 累加）
3. 把沿途边的 `path` 拼起来 → **真实走线**

名字对不上无所谓，**物理路径是客观的**。

## ★ 三道守卫（缺一不可）

这三道都是被实际错误逼出来的，**去掉任何一道都会在地图上画出假线**。

### 1. 端点距离 ≤ 300 km

```
九州 大平人吉線 (人吉ss → 大平ss)   直线距离 1,358 km
```

人吉和大平都在九州，九州南北才约 350 km。**「大平」在北海道也有一个同名变电所** ——
地图上会出现一条横跨日本的虚构输电线，**且不报错**。

⚠️ **不要用「区域必须一致」来防这个**（我一开始就是这么干的，错了）：
AJG 的 `region` 是**地理地方**，OCCTO 的 `対象エリア` 是**电力区域**，两者不等价。
いわき（福島県）地理属 tohoku、供电属東京電力；西播（兵庫県）被 AJG 标成 chugoku。
按区域硬拒会把 `新いわき`『南いわき』『新福島』`西播` 这些**真实存在的站全部误杀**
（实测误杀 4.1pt）。**防跨岛误配靠距离，不靠区域。**

⚠️ 两道距离守卫必须在**同一个函数**里查。早先「放宽电压」的回退分支只查了绕行比、
没查绝对距离，1,358 km 那条就是从那个口子漏进来的。

### 2. 绕行比 ≤ 2.0x

路径长度不得超过两端直线距离的 2 倍。超过说明 Dijkstra 绕了远路。
加守卫前最长路径 **1,704.7 km**（日本南北才约 3,000 km），加后 **392.0 km**。

### 3. 电压过滤

500kV 的潮流不该绕经 66kV 线路。按潮流 CSV 的 `電圧` 限制可走的边；
严格约束下不通时才放宽（占 3.4%，这部分标记出来供核查）。

## ⚠️ 罗马字 name 陷阱（踩过，影响全链）

```json
"name":    "Nishifutaba Switching Station",   ← OSM 的 name 有时是罗马字
"name:ja": "西双葉開閉所"                       ← 日文在这里
```

写成 `p.get("name") or p.get("name:ja")` 会拿到**英文名**，于是
`西双葉開閉所`『旭川嵐山開閉所』『双葉開閉所』**从未进过索引**，
而我一度把它判定为「AJG 缺这些站」。

修法：**所有名称变体（`name:ja` / `name` / `name:en`）都进索引**。
`built/all.json` 的节点只有单个 name 字段，所以按坐标（600 m 内）
把原始 `{region}_substations.geojson` 的全部变体贴回图节点。

修完直接见效 —— 这三条从「全部失败」变成成功：

```
道南幹線  (西双葉SWS → 北斗CS)      172.0 km  绕行比 1.72x  ✅
函館幹線  (双葉SWS → 北七飯SS)      162.9 km  绕行比 1.71x  ✅
道北幹線  (旭川嵐山SWS → 西当別SS)   123.1 km  绕行比 1.32x  ✅
```

## ★ 端点索引必须包含発電所（踩过，+12 条）

潮流 CSV 的端点里有大量**厂内变电所**：

    金武火力変電所・具志川火力変電所・吉の浦火力変電所・石川火力変電所

AJG 侧叫「金武火力**発電所**」，而 `norm_station` 两边都归一成「金武火力」——
**本该对上**。但早先端点索引只收 `*_substations*.geojson`，
**発電所根本没进来**，实测沖縄一个区域因此卡住 37 条线次（该区 31 条线全部失败）。

两处修法：

1. **索引加入発電所**，但只收 `plants_utility` + `generators` 这两个**事业用**图层。
   ⚠️ 不要用全量 `{region}_plants`（19,138 个，绝大多数是小太阳能）——
   归一后名字很短，进索引只会制造撞名误配（同 `PLANT_MATCHING.md` 的「静默错误 A」）。
2. **贴附半径按设施类型分开**：変電所 0.6 km、**発電所 2.5 km**。
   発電所厂区大、引出线接入点常在数 km 外；用同一个 0.6 km 的话，
   `吉の浦火力`/`金武火力` 会出现「AJG 里明明有数据却贴不上」。
3. **对所有节点贴附邻近设施名**，不只 `sub==1` 的 ——
   発電所引出线接入的图节点常是 junction（`sub=0`）。

合计 69.6% → **72.2%**。

## ❌ 走不通的路：自建图（`rawgraph.py`）

**结论：不要用，继续用 AJG 的 `built/all.json`。**

当时的假设是「AJG 缝合把 40,077 条线段丢成 19,031 条边，丢了 53%」。
**这个假设是错的** —— 那是**合并**不是丢弃（AJG 把共线的多个 OSM 线段并成一条边，
`lines_all.geojson` 恰好也是 19,031，与 built 边数完全相等）。

自建图（原始线段 + 端点吸附）实测**更差**：

| | AJG built | 自建（sub-snap 300m） |
|---|---:|---:|
| 主连通分量占比 | **65.9%** | 56.7% |
| 连通分量数 | 1,096 | 2,545 |

AJG 的缝合（`n_stitch: 400`）比朴素端点吸附高明得多。`rawgraph.py` 保留作为
**否定结论的证据**，不要再走这条路。
