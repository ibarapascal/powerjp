> 目的：把对话里散落的前端要求固化下来。**改视觉之前先读这个文件。**
> 结构：① 不可违背的原则 ② 具体规格 ③ 待做 ④ 已否决
> 更新规则：用户每次给新反馈就往对应小节加，**注明日期**。

## ① 不可违背的原则

| # | 原则 | 出处 |
|---|---|---|
| P1 | **几何绝不简化** —— 不做 Douglas-Peucker、不按缩放抽稀、不合并顶点 | 2026-08-02「一定不要做简化」 |
| P2 | **不因为密而隐藏要素** —— 不用 `minzoom` 藏图层。「看不清」用颜色/透明度/叠放顺序解决，不靠删 | 2026-08-02「太密没事，放大能看就行，不要缺东西」 |
| P3 | **实测与推算必须视觉可分** —— 实测＝实心+白描边，推算＝空心圆，面板给黄色警告 | 一贯要求 |
| P4 | **潮流的叠加只改颜色，不改粗细** —— 粗细唯一由电压决定 | 2026-08-02，反复强调过两次 |
| P5 | **不擅自调「发挥」** —— 宽度档位等既定数值不要自己改梯度 | 2026-08-02「不是让你发挥」 |
| P6 | **不画错的几何** —— 宁可线断开，也不画物理上不存在的连接 | 2026-08-02「不能画错的」 |

## ② 具体规格

### 送電線

- 配色**只用青系**，靠彩度区分 5 档。⚠️ **最高压不要往白靠** ——
  `#d6ecff`（明度 .82）会让并走的潮流线看起来「镶了白边」。用彩度不用明度
- 粗细也分 5 档，与颜色同档
- **唯一定义**：`layers.ts` 的 `KV_LINE_WIDTH`。送電線・潮流・流光三者共用

| 电压 | 色 | 宽（z4 / z11） |
|---|---|---|
| ≥500kV | `#29c3ff` | 3.2 / 7.4 |
| 275–499 | `#3fa9e8` | 2.2 / 5.2 |
| 154–274 | `#4f93cc` | 1.5 / 3.6 |
| 66–153 | `#4a7099` | 1.0 / 2.4 |
| <66 / 不明 | `#3f4c5e` | 0.6 / 1.6 |

### 潮流

- **底色和送電線完全一致**（电压青系、同宽）。潮流本身不改变线的颜色和粗细
- 潮流的信息**全部由流光承载**：
  - 流光的**颜色** → 负荷率（见下）
  - 流光的**移动方向** → 潮流正方向
- **几何按区间电压细分**：一条潮流线跨多个电压时（335 条里有 12 条），
  每段用各自的实际电压，宽度才能和底下的蓝线逐段对齐

### 潮流几何的取舍（P6 的具体规则）

用户 2026-08-02 的原话：「实际是很近的地方可能单纯是 500kV 没连到一起，
然后中间的部分 OSM 那边数据是**未分类**而不是就是明确的小线路，那我觉得留着 ok」

| 区间质量 | 判定 | 画不画 |
|---|---|---|
| `real` | 有真实几何，且段电压与线路电压不冲突 | ✅ |
| `short_gap` | 无几何（直线兜底）但 **< 1.5km** —— 近距离的连接缺口 | ✅ |
| `straight` | 无几何且长 —— 会画出**不存在的直连** | ❌ |
| `kv_mismatch` | 段电压 < 线路公称的 50% —— 路径迷进了别的线路 | ❌ |

⚠️ **段电压 = 0（OSM 未分类）不算错误** —— 那是「不明」，不是「已知是低压」。

实测排除 180 区间 / 468 km（含 275kV 线路误走 77kV 线达 22.6km 的情况）。

### 幾何の重なりは**そのまま**にする

異なる線路が同じ区間に重なることがある（実測 156 区間 / 23%）。
経路探索は両端しか知らないため別々の線路が同じ辺に載る一方、
日本は**同塔並架**が多く重なりが物理的に正しい場合もあり、
データからは両者を区別できない。

⛔ **オフセットで描き分けない**（2026-08-02「因为线宽也有定义，所以就重叠得了」）。
線幅は電圧で一意に決まる決まりなので、オフセット量を線幅に追従させると
幅の定義が二重になる。**重なったままでよい**。
クリック時に `shared_count` / `shared_with` で何本共有しているかだけ示す。

### ★ 地图的线来自**原始数据**，不是拓扑图

⛔ 前端的 `grid_lines` 必须从 `data/{region}_lines.geojson`（原始 OSM 提取）生成，
**不要从 `built/all.json`（拓扑图）生成**。

拓扑图是为**连通性**构建的，接不上的线被丢弃了（架空 18%、地下电缆 56%）。
但画一条线不需要它接得上——「能画」和「能算拓扑」是两件事。

```
原始 data/*_lines.geojson    40,931 条  ← 地图用这个
built/all.json               14,048 条  ← 潮流路径求解用这个
差额                         26,901 条（66%）从来没显示过
```

每条线带 `in_topology` 标记，前端分成三个图层（各自 checkbox）：

| 图层 | 内容 | 表现 |
|---|---|---|
| 送電線（系統に接続） | 14,030 条 | 不透明度 0.92 |
| 送電線（接続情報なし） | 26,901 条 | 同色同宽，**不透明度 0.45** |
| 地下ケーブル | 1,271 条 | **静的破線** `[2, 1.5]` |

- 颜色和线宽**始终由电压决定**，三层共用 `KV_COLOR` / `KV_LINE_WIDTH`
- 地下线的不透明度按 `in_topology` 变，两个维度不打架
- ⚠️ 虚线是**静态**的，不做动画——避免潮流流光那次
  「data-driven 宽度 + 动画 dasharray → 部分线闪烁」的坑

### ⚠️ 直线过滤：只挡「2 点且 >2km」，不要按点密度

`grid_lines` 里 2 点的线段有 16,675 条，但 **2km 以上的只有 7 条**。
铁塔之间一跨本来就是两个点，那是 OSM 的数据粒度，不是直线近似。

⛔ **不要用「点密度」过滤。** 1 点/km 以下的 9 条里，8 条是**海底电缆**：

```
0.09 点/km  33.5km  HVDC Hokkaido-Honschu    ← 北本連系線
0.15 点/km  46.4km  阿南紀北直流幹線          ← 紀伊水道
0.12 点/km  51.6km  松島奈良尾線(五島連系線)
```

海底铺设不绕地形，**直线就是真实形状**。按密度过滤会删掉跨区域的关键联络线。
真正画得粗的只有 `水道橋線`（10.4km / 4 点）一条，为它一条误删 8 条不划算。

> HVDC 那几条 `in_topology=False` 是**正确的** —— 直流线路本就不在交流拓扑里。
> 现在它们能显示但不参与潮流求解，这个区分正好。

### 変電所：不加描边

⛔ **不要给变电所加 `circle-stroke`。**（2026-08-02「变电站去掉 border 试试」）

变电所有 8,994 个、半径只有 1.2–5.5px。原来那圈 0.5px 的暗色描边
（`#0b0f14`，和底图同色）会把每个点边缘啃掉一层，小尺寸下**电压配色基本读不出来**。

密集处糊在一起是预期的，用不透明度（0.85）调，不靠描边分隔、更不靠隐藏（P2）。

### 変電所：种别只写清楚，不着色 —— ⚠️ 部分被 2026-08-07 取代

> **2026-08-07 的变更**：种别改为**每类一个 checkbox**（见下面「変電所：种别独立勾选」）。
> **不变的部分**：颜色仍然只表示电压，不按种别分色 —— 下面那条判断依然成立且被再次确认。
> 变的只是「种别放哪里」：从「只在信息面板」变成「面板 + 独立勾选」。

**要求（2026-08-02）**：「图例不需要每种不同颜色，但是描述要准确」。

那 8,994 个点**不全是变电所**：配電用 4,235／送電用 2,690／鉄道用 789／
需要家 352／架空・地中の切替所 169（连「所」都不是）／開閉所 137／
発電所構内 45／変換所 28／調相 15／不明 534。

因此：

- 图层名 **「変電所・開閉所ほか」**，`note` 里逐类写出数量
- **颜色仍然只表示电压**，不按种别分色（10 类，配色会打架且没人读得出来）
- 种别放在**点击后的信息面板**：`stype_ja` + `stype_source`
- ⚠️ `stype_source: voltage` 是**电压推定**（2,315 件＝26%），面板上标「⚠️ 電圧からの推定」，
  不能和 OSM 实标数据长得一样

> 字段已经在 `substations.geojson` 里（`stype` / `stype_ja` / `stype_source` / `trunk`）。
> 将来要按种别过滤或着色，前端加个 filter 即可，不用再动管线。

原话：「颜色我觉得不需要区分，主要是类别让能独立勾选比较重要」。

**颜色不动**（仍是电压青系），种别靠 **checkbox 出入**。这样不消耗色相 ——
地图的色相预算已经用满：青系＝电压、黄橙赤＝负荷率、电源种 8 色也画成**圆点**，

8 个图层，收在**父节点「変電所・開閉所ほか」**下（多级 checkbox，**默认展开**）：

| 图层 | stype | 备注 |
|---|---|---|

| 配電用変電所 | `distribution` | |

⛔ **件数不要写进 label**（2026-08-07：「件数为啥要写死，肯定要改」）。
`LayerDef.count = { prop, values }` 声明怎么数，`MapView` 读到 GeoJSON 后
从**实际数据**算出来。上游更新后数字自动跟着变。

⛔ **不要平铺**（2026-08-07：「做成多级 checkbox 不是平铺开加这么多」）。

点它一次性切换全部子项；`▸/▾` 展开收起。

⚠️ **`その他` 和 `種別不明` 不能合并** ——「知道是别的种别」和「不知道是什么」
是两种信息。repo 在别处（`data_quality` / `connectivity_confidence` / `stype_source`）
一直分得很清，这里合掉会不一致。

⚠️ 默认**全部 OFF**（2026-08-07「设施相关嵌套 checkbox group，默认让不显示」）。
8,994 点在初始视图太密。要看哪类自己勾。
⛔ 别以「空着不好看」为由改回默认 ON。
（父节点在侧边栏里仍然**默认展开**，能看到有哪些种类可选。）

### ★ 潮流的方向：不能用绝对值

⛔ **OCCTO 的「潮流方向(正方向)」是参照方向，不是实际流向。**

各线路有一个约定的基准方向，值以它为正——**负值表示实际反向流动**。

实测（2026-07-31）：**464 条线里 189 条（41%）平均潮流为负**。
福冈的例子：

```
脊振西福岡線   正方向「西福岡ss → 脊振ss」   实际 −486MW
             → 真实流向是 脊振 → 西福岡（流入市区）
```

早先用 `abs()` 取平均，符号丢了，流光一律沿几何方向跑，于是
**流入负荷中心的电力被画成流出**（用户 2026-08-02 发现「福冈市区的潮流怎么都是往外走的」）。

~~**修法**：publish 时若带符号的平均为负，反转几何坐标序列。~~
**⚠️ 这个做法在 2026-08-02 被推翻，见下节。**

### ★★ 潮流的方向会随时间变（2026-08-02）

实测：7 天窗口内 **464 条线里 184 条（40%）会改变方向**，少数侧占比中位数 13%。

所以上面那个「按当日平均反转几何」的做法**作废**。方向必须**按当前时点判断**，
不能一条线固定一个方向。

> 实现（10 层、dasharray 不能 data-driven、为什么不用 setData）见
> `flowGlow.ts` 的注释与 `LESSONS.md` #40。

### 时间轴

**要求（2026-08-02）**：「不需要时序播放，可以回溯 24 小时就行，像 windy 那样，
默认当前最新的，然后可以有 step 的往前拖动」。

| # | 要求 |
|---|---|
| T1 | **默认停在最新数据那一格**（2026-08-02「默认停在最新的数据那里」） |
| T2 | ⛔ **没有自动播放**。只能手动拖 |
| T3 | 可往前回溯。窗口取 **72 小时**（要求是 24，看情况放宽，已确认「24或者72，看情况」） |
| T4 | **潮流和机组共用同一条时间轴** —— 两者显示不同时刻就是在撒谎 |
| T5 | 窗口是**滚动的过去 N 小时**，不是「当日」（2026-08-02「改成浮动过去 24 48 或者 72」） |
| T6 | 刻度做成**物差し**：日 / 6h / 3h / 1h 四级，数字每 3 小时（2026-08-07） |
| T7 | **调整力没有的区间要区分出来**，不能默默通过（2026-08-07） |

#### T6 刻度尺

```
日   ┃              ┃              ┃     9px
6h   ┃      ╷       ┃      ╷       ┃     6px
3h   ┃  ╷   ╷   ╷   ┃  ╷   ╷   ╷   ┃     4px
1h   ┃╷╷╷╷╷╷╷╷╷╷╷╷╷ ┃╷╷╷╷╷╷╷╷╷╷╷╷╷ ┃     3px
     03 06 09 12 15 18 21
8/4                  8/5
```

⚠️ 四级**靠长度区分，不靠颜色** —— 颜色是数据的（见「设计方向：計器盤」）。
⚠️ 数字每 **3 小时**一个。6 小时一个的话一天只有 3 个数字，太粗
（2026-08-07「现在时间刻度只看到 6 12 18 啊，再细一点」）。

#### T6b 刻度上的星期（2026-08-07，当日内改过两次）

先是「不加星期」，后改为**加上，但不参与居中计算**。最终形态：

```
   00  03  06  09  ...
  8/4 Tue
   ↑ 「8/4」的中心对准 0 时的刻线，「Tue」挂在右侧
```

⛔ **星期和它前面的空格不能计入水平居中。**
日期用 `translateX(-50%)` 居中于 0 时刻线，如果星期也算在宽度里，
日期就会被推向左边、对不上刻线。而且**星期的字宽逐日不同**
（`Tue` vs `Wed` vs `Fri`），算进去的话每天偏移量还不一样。

实现：星期是 `position: absolute; left: 100%` 的子元素，**不占父元素宽度**。
⛔ 别把它改回普通行内元素。

#### T8 窗口必须是**滚动的 72 小时**，不是「最近 3 天」（2026-08-07）

原话：「这个刻度 72 小时，你要根据现在的时间平移的」。

⚠️ 这条 T5 早就写了，但实现一直是按**整日**切的，是个真实的 bug：

```python
n_days = -(-FLOW_WINDOW_H // 24)   # 72/24 = 3 天
days = days[-n_days:]              # ← 整日切片，窗口头锚死在日界
```

症状：窗口是 `8/4 00:00 〜 8/6 21:00` = **69.5 小时**，而且时间往前走时
**头部不动**，要等跨日才整块跳一天。

修法（`load_flow_slots`）：多读 **1 天**，去掉末尾未到来的格之后，
**从末尾往回数 `FLOW_WINDOW_H × 2` 格**。现在是 144 格 = 整 72 小时，
头尾都跟着最新实测滑动。

#### T9 时间轴是**点**不是区间（2026-08-07）

原话：「是不是不需要加 range，直接当前的拖动就行，毕竟不是一个范围」。

⚠️ **元素保持 `input[type=range]`** —— HTML 的 `range` 指 min〜max 的取值
范围，本来就是**单值滑块**，不是区间选择器。换成自写 div 要重做方向键、
触摸、ARIA。

⛔ 但**不要把游标左侧填成实色**（浏览器默认行为 / `accent-color`）。
填了就像「起点到现在被选中」，这才是「看起来像区间」的真正来源。

- 轨道端到端**等粗等色**（2px `#2b3441`）
- 游标是**竖线**（2px × 16px），不是圆形把手 —— 和刻度尺同一套语言

#### T10 现在位置的指针（2026-08-07）

`input[type=range]` 原生 thumb 能做的样式有限，所以**把 thumb 设成透明、
只留 20px 拖拽热区**，视觉另画 `.timebar-cursor`：

- **圆点 13px** + 2px 深色环 + 淡光晕 + 阴影
- **一条竖线**从圆点向下渐隐到刻度尺 —— 圆点单独存在时无法和刻度对齐读数
- **脉动**：只让外圈光晕扩散淡出（2.4s ease-out），**圆点本身不动**
  —— 圆点一动会读成「时刻在漂移」，而它标的是一个精确的 30 分格
- `prefers-reduced-motion: reduce` 时不播放

⚠️ 圆点大小反复调过：9px（太小看不见）→ 13px。**可见性优先于精致**。
⛔ 别为了「配合刻度尺的细线语言」把它改细，试过，位置就找不到了。

⚠️ **脉动不是自动播放**（T2）。时刻不会自己走，动的只是位置标记。

#### T11 刻度的线也要 4.5:1（2026-08-07）

| 6h 刻 | `#5b6675` **3.30** | `#939dab` 7.00 |
| 日刻 | `--text-dim` 9.29 | 不变 |

⛔ 别以「线细所以可以淡」为由调暗 —— **最细的线恰恰是淡了就消失的那个**。

#### T7 机组欠测区间

`occto_unit` 是 **T+1 公表**，所以潮流有值的时段里，机组最多可能整天没有。
默默通过会让人以为**全国机组停机**。

- publish 输出 `unit_last_idx`（**事实**：机组实测到哪一格）
- 时间轴在其后画**橙色斜线带**，边界一条竖线
- 拖进该区间时，头部出现 `調整力データなし` 徽章
- 默认位置 = `unit_last_idx`（潮流和机组都有值的最后一格）

⚠️ **publish 只报事实，不决定 UI 默认值。**
早先版本让 publish 输出 `default_idx`，等于把显示逻辑埋进管线 ——
改个默认位置就得重跑 pipeline。已改为前端从 `unit_last_idx` 自己算。

#### T12 欠测时机组仍画圆环（2026-08-07）

原话：「调整力机组没有数据的时候，仍然能显示圆圈，只是内部没有扇形」。

⚠️ 但「圆环 + 无扇形」和**出力为 0（停机）**是同一个画面。所以欠测用**虚线圆环**：

| 画面 | 含义 |
|---|---|
| 实线圆环 + 扇形 | 有数据，正在发电 |
| 实线圆环 + 无扇形 | 有数据，**出力为 0（停机）** |
| **虚线圆环** | **没有数据** |

⛔ **不要把欠测藏起来**（早先版本用 filter 整个不画，会读成「这里没有发电所」）。
⛔ **不要把虚线改回实线**，那就和停机混了。
⛔ **不要用透明度区分**（2026-08-07 明确否决）—— 薄了会读成「在弱发电」。
**数据的有无**和**发电的量**是两个轴，不能挤进同一个视觉通道。

图标名沿用 `fsteps` 的 `-`（`pie-gas--`），不用改数据格式。

### 圆（発電所）

#### 大小 ＝ 装机容量、**全设备统一一套刻度**

⛔ **不要给不同图层各自的刻度。**（2026-08-02「不要有不一致的，我现在看到 30mw 和
3000mw 的有的几乎大小一样，这个完全不对」）

之前 `plants` 用 10–5,400MW、`sites` 用 1–365MW 两套独立映射，
于是 30MW 在小尺度里接近上限、3000MW 在大尺度里也接近上限，画出来一样大。
现在统一 **1MW–6,000MW**，`capRadius()` / `capIconSize()` / `capStrokeWidth()`
全部从同一个 `capT()` 派生。

#### 刻度是 **0.4 次幂**，不是对数也不是面积正比

| 30MW vs 3000MW | 1MW | 30MW | 3,000MW | 比 |
|---|---:|---:|---:|---:|
| 面积正比 sqrt | 3.0px | 4.3px | 19.2px | 1:4.4，但中间段塌陷 |
| 对数 ln | 3.0px | 12.0px | 24.2px | **1:2.0，差不出来** |
| **0.4 次幂（采用）** | 2.5px | **5.4px** | **26.2px** | **1:4.8** |

两次都调过头过：面积正比是「大的太大」，对数是「小的太大」
（`ln(30)/ln(6000)` 已占 39%）。0.4 次幂在两者之间，中间段 100–1,000MW 不塌陷。

上端 26px → **34px**（2026-08-02「大的可以稍微更大一点」）。

> 两个旋钮分开：**`P`（指数）控制曲线弯曲**，**端点值控制整体大小**。

#### ⚠️ 描边宽度也要随大小变

⛔ **不要用固定值。** 半径 2.5px 的圆配 1.6px 描边 → **描边占了 64%**，
小点看起来全是边框（2026-08-02「小圈的 border 有点大」）。

`capStrokeWidth()` 用同一条 `capT()`，让描边占半径的比例大致恒定：

| 容量 | 半径 | 描边 | 占比 |
|---|---:|---:|---:|
| 1 MW | 2.5px | 0.60px | 24% |
| 100 MW | 7.8px | 1.01px | 13% |
| 6,000 MW | 34.2px | 3.01px | 9% |

#### 内部扇形 ＝ 实时功率百分比

- ⚠️ 扇形是**该时刻的出力 ÷ 容量**（`load`），**不是当日累计的设备利用率**（`cf`）
- 实测差异：原町 实时 94% vs 当日平均 48%；船町 实时 0% vs 当日平均 39%
- 停机座数：实时口径 67 座为 0，平均口径只有 32 座
- 停机时圆环仍在、扇形为空 →「有电站但没发电」和「没有电站」可区分
- 实现：canvas 生成「电源种 × 利用率 21 段」共 147 个图标 + symbol 图层
  （`circle` 画不出扇形）。`icon-allow-overlap: true` 保证密集处不隐藏
- ⚠️ **`icon-size` 的除数是 56 不是 64** —— 图标里画的圆直径是
  `ICON_PX - 8 = 56`，留了 8px 给描边。用 64 换算会让 symbol 比 circle 小 12.5%

### ★ 时序 chart（2026-08-07）

原话：「点击潮流、调整力机组的时候，和 timeline 对称的，地图上方显示一个时序 chart，
潮流就是潮流，调整力机组就是出力…或者直接放到 timeline 上方紧贴着也行」。

**放在 timebar 内部、刻度尺正上方**，和刻度**共用同一套横向百分比坐标**。

⛔ **不要挪到地图上方另开一块。** 两套坐标系对不齐，
「这个尖峰是几点」就读不出来了 —— 而那正是这个图的主要用途。
现在曲线的峰、日界线、小时刻线、游标是逐像素对齐的。

| 项 | 做法 |
|---|---|
| 潮流 | **带符号**，0 线居中 —— 能看出窗口内哪几段方向反转 |
| 机组 | 出力，0 线在底 |
| 欠测 | **断开不连线**，面也分段闭合。⛔ 用 0 连过去会读成「出力掉到 0」 |
| 线 | `stroke-width: 2`、`--text`、`non-scaling-stroke`（横向拉伸不变粗细） |
| 阴影 | 线下方到 0 线的垂直渐变，`--text-dim` 34% → 0 |
| 值域 | 只标上端（`±2,800 MW`）。⛔ 不画完整坐标轴，轴比曲线还抢眼就本末倒置 |
| 出入 | `grid-template-rows: 0fr → 1fr` 折叠动画，关闭时中身多留 220ms 再卸载 |

⚠️ 变电所等**没有时序的要素不出图**。
⚠️ 已知边界：潮流图层关掉时 timebar 整个不渲染，chart 也就没了。
